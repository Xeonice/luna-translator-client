# LunaTranslator Rust 完整产品规划

版本：PRD 1.2；原生视觉设计契约：`aligned-v1`（PRD 1.1范围）；原生稿确认日期：2026-10-13。PRD 1.2增加compat_windows范围与流程，并明确常驻浮窗及独立实时OCR翻译工作流；2026-10-16补充Windows x86游戏目标的自动架构路由，`compat-x86-v1`新增8张可编辑原生设计样张为not_reviewed，未捕获状态仍planned。

本产品面向希望 fork、检查和长期维护 LunaTranslator 的使用者，以 Rust 为主实现桌面宿主、数据与翻译管线，承接原产品的游戏翻译、阅读学习、语音、游戏管理及网络服务能力。游戏内继续使用适合引擎的 Python、JavaScript、托管插件或原生提取器，通过稳定 bridge 接入宿主；迁移不要求把每个脚本和每条引擎规则逐行改写成 Rust。

**实时OCR翻译是独立使用方式**：用户在其他应用前台时，用全局“框选实时OCR区域…”快捷键或菜单唤起目标屏幕的临时选区覆盖层，直接拖出矩形；松手即提交范围并开始持续识别，把识别原文送入常驻翻译浮窗并实时展示译文。无需先打开主窗口或在缩略图上选区；应用窗口绑定保留为次级可选方式。课程视频、会议字幕及其他应用画面均可作为使用场景，不要求游戏库记录、游戏启动或HOOK连接。OCR读取图像，与直接从游戏引擎/进程获取实时文本分别验收；OCR成功不证明游戏已可直接接入。

macOS 的游戏范围同时包含原生游戏与通过CrossOver/Wine等运行的Windows游戏。execution_environment区分`native`与`compat_windows`：前者保留原生Mac接入与架构lane，后者采用“Mac宿主＋同bottle helper64/Host64接收端＋同源injector32/64＋目标匹配Hook32/64”的规划路线，复用Windows LunaHook和引擎规则；此路线已由用户选定，新增x86链路已进入实现和受控工程验证，原版游戏及完整接入尚未验收。Mac原生分支复用文本语义、方法选择器和过滤规则，独立适配进程接入、原生库定位、ABI、拦截器与IPC；兼容分支另外验证bottle内目标、helper、注入与跨环境传输。产品按具体游戏、版本、执行环境及入口证据展示状态，不能把“能编译”“fixture能取文本”“Windows原机通过”或“同名引擎有规则”写成真实Mac游戏已支持。

这是完整产品范围，P0、P1、P2表示交付依赖与先后顺序，后续阶段的需求不从产品范围删除。所有新客户端功能在本文均为待实现的规划；“文档已有”仅说明上游基线，不能视为本项目完成状态。

## 基线与范围

上游基线固定为 `HIllya51/LunaTranslator@c8701872a5de83f8d3272f3967457d0b8f2983c4`。29篇中文产品文档、模拟器引用清单和必要源码补充逐篇映射在 [功能来源表](00-source-map.md)。本规划使用其中的SRC编号注明来源；代码、外部模型、第三方账号和资源包的可用性分别验证。

**范围内**：Windows原机、Mac原生及Mac compat_windows游戏的HOOK与内嵌接入规划，原生模拟器、独立实时OCR识别与翻译（屏幕框选/绑定应用窗口→识别原文→常驻浮窗实时译文）及一次补充识别、剪贴板/手动/文件输入、传统与LLM/离线翻译、处理和优化词典、注音查词与Anki/Yomitan、TTS/语音识别、游戏库/元数据/时长/备忘、浮窗/截图/系统工具/快捷键、网络API、多配置、数据迁移、更新诊断与维护者工作流。

**范围边界**：不承诺所有视觉小说、全部模拟器游戏或所有商业签名进程可外部attach；不自动削弱系统保护或修改发行包签名来制造覆盖；不内置重写Anki同步协议；不把Windows WebView2、GDI、SAPI、LiveCaptions、Magpie等特定实现当成Mac能力；文件翻译第一版规格只覆盖TXT、JSON、SRT、VTT、LRC，不含任意Office/PDF转换。

**Windows游戏目标架构范围（2026-10-16）**：在支持的64位Windows或macOS客户端/兼容runtime上，纳入PE x86与x64游戏目标；“支持32位游戏”不扩展为32位操作系统或32位主客户端承诺。默认保留helper64/Host64接收端，应用自动检测实际游戏目标PE架构：x86选择同源injector32/Hook32，x64选择injector64/Hook64。Host匹配其装载进程，injector/Hook匹配游戏目标，不跨位数装载DLL。不同位数产物分别锁定来源、协议版本与hash，必须验证跨位数通信和取消清理，不能由构建或x64实测外推x86。固定`memo01/Game.exe`为本次x86设计示例与后续原包候选；Ever17修复版仅保留来源待核的资源线索，不作为原发行GC验收依据。

本期客户端宿主只覆盖Windows PC与macOS，Linux、iOS、Android原生客户端不在当前交付；现有Web/API的浏览器访问仍在范围内。两端必须维护同一套UI：Tauri 2承载共享React/TypeScript页面、组件、主题tokens和command绑定，涵盖22页、常驻HUD与选区；OS差异仅通过系统adapter、语义token及键位映射表达，不复制完整页面或另建原生产品UI。Windows/Mac最低OS与具体CPU lane在D1以实际依赖、包和运行证据锁定，不凭框架的理论支持范围承诺。选定路线及依赖见[客户端架构§2.6–2.8](03-client-architecture.md)。

原生Mac兼容记录不得只以引擎名为主键。记录至少包括游戏名称与来源、版本或可识别hash、CPU架构、runtime版本、原发行签名状态、系统版本、接入方式、取文/回写能力、已验证步骤与失败原因。开发fixture、用户提供插件入口、原发行包和重签名副本分别标记；fixture成功不会提升原发行包的覆盖状态。

macOS的compat_windows列是新增规划，以上Mac原生列不代表该路径。兼容路径优先复用Windows helper/DLL和规则，再通过受控bridge将事件送入Mac Rust核心；bottle内进程发现、Windows注入API、PE架构、IPC可达性与内嵌均逐项验证。游戏能在CrossOver/Wine启动只证明启动阶段，不证明可HOOK；Mac屏幕捕获/窗口权限仍由Mac host侧判断。Windows专用系统工具、语音或扩展不因运行于bottle自动获得等价支持。

compat_windows记录至少增加host_os/host_arch、兼容产品及版本、Wine/runtime版本、bottle_id、Windows目标路径/版本/hash、target_arch/helper_arch、入口及bridge版本；Mac host进程/窗口身份与bottle内Windows target身份分别保存。原生Mac仍单列Intel x86_64、Apple Silicon arm64和Rosetta x86_64，不把Rosetta原生Mac程序归入compat_windows。不同bottle、运行环境或重建实例不得共用裸PID/句子身份或未经检查的绑定；fixture、原包、不同产品/runtime及bottle配置分别出结果。

## 输入与游戏接入需求

US-01的关键区别是“默认输入源”和“临时一次输入”。切换默认源会改变持续采集器；一次OCR、读取剪贴板或手动文本可以经过同一翻译管线，而不改变正在运行的HOOK会话。

- **REQ-001 统一输入与状态** — P0；文档已有并新增统一状态规格；SRC-02、SRC-05、SRC-09、SRC-12；SCR-01、12、13。默认源包含HOOK、OCR、剪贴板、语音识别；也可选择手动模式，此模式不启动自动采集。手动文本、文件任务和网络输入可独立进入。区分连接、采集运行/暂停、翻译总开关与原文/译文可见性。每条输入附游戏/会话/源标识，临时输入不能改掉持续源。
  - 验收：HOOK运行时执行一次OCR后，后续HOOK句子继续进入；暂停自动采集后手动执行仍能读取一次；关闭翻译不会错误显示为“连接断开”。切游戏后旧会话的延迟结果不能覆盖新游戏。

- **REQ-002 进程选择与连接** — P0；文档已有，Mac原生与compat_windows接入为新增适配；SRC-01、SRC-05、SRC-14；SCR-04、21、22。显示进程名称、可执行路径、架构与窗口，支持刷新、筛选、连接/断开、重试。先区分native与compat_windows；兼容环境显示产品/runtime、bottle和其中的Windows目标，不用Mac host PID冒充Windows目标PID。主路径由Mac客户端在用户选择游戏/bottle并点击连接后自动启动及管理同bottle PE helper，依次检查环境、启动helper、握手、连接目标和等待文本；用户无需安装或手动打开另一Windows客户端、复制DLL或执行命令行。首次无法关联bottle时在SCR-04显示可取消确认，明确后再启动；失败提供重试、修正bottle、诊断及备用手动启动入口。普通连接、等待延迟或目标模块就绪、权限不足、缺组件、目标已退出、架构不符分别反馈；等待可以取消、超时和重试。只有明确需要时使用Windows提权分支，不能把提权或helper启动写成兼容环境必定可注入。
  - 验收：按保存的环境/bottle一键连接时正确helper自动启动并完成受控握手，缺失/未知关联先确认且可取消；启动、组件就绪、目标连接与实际取文分阶段，不无限展示“正在注入”。应用自动选择接收端与目标侧组件，不要求用户手选位数或安装DLL；缺32位资源、错误Host/injector/Hook组合在注入前阻止，并提供修复同源资源包、重新检查、修正bottle和OCR入口。修复组件不等于游戏已支持。同名多进程用环境、bottle、路径及目标身份区分；bottle缺失、helper不可用、桥接不可达、架构不匹配及目标退出分别给原因。关闭sheet取消本次接入但不终止游戏；断开仅清理本次自有helper/agent，不执行wineserver kill或关闭整个bottle；注入后取消需确认detach回执，无法确认时标记目标内状态未知并指导重新检查，不凭helper退出声称卸载成功。切换或重建bottle后旧连接与迟到结果不得影响新目标；App启动不自动扫描并注入所有游戏。

- **REQ-003 引擎HOOK策略** — P0；文档/源码已有，原生与兼容环境适配；SRC-05、SRC-14、SRC-C04至SRC-C08；SCR-04、13、22。复用引擎识别、语义方法、过滤与规则来源；Windows现有二进制可先保留，compat_windows优先尝试同bottle Windows helper/LunaHook与PE规则。策略层描述提取目标，平台backend负责定位/取参/拦截，不把所有规则重写作为前置；Mac原生Mach-O与兼容环境PE的定位、ABI、指令规则和安装能力分别验证，不直接互换地址。未匹配时提供特殊码、OCR或手动输入入口。
  - 验收：相同提取器的文本过滤与分流fixture在可用backend得到一致结果；规则/hash与集中shim差异可检查。Windows原机、Mac原生与compat_windows的成功证据互不代用；一个backend不可用时不宣称引擎已覆盖；规则来源、版本与失败阶段可查。

- **REQ-004 HOOK文本流选择** — P0；文档已有，显式保存与草稿恢复为新增规格；SRC-05、SRC-14、SRC-26；SCR-05。候选流显示名称、预览、历史、字符编码与取文/回写能力。候选表默认按首次出现排序，表格排序与有序翻译选择分别管理；可选一条或多条，按显式合并顺序组合人名与正文。当前会话选择与“保存到游戏”的持久快照分开，保存稳定流描述符、合并顺序和规则版本；重连仅恢复能匹配的流。
  - 验收：重新排序候选表不改变合并结果；新增流不替换当前选择；取消流后不再进入合并。无候选时不伪造默认对白、不允许保存空选择覆盖旧快照；未保存的修改不冒称已保存，保存失败保留编辑。重连后失效描述符保留标记并要求重选，不静默选错流；候选缓存设置不删用户翻译历史。

- **REQ-005 HOOK参数** — P0；文档已有；SRC-14；SCR-03、13。提供刷新延迟、最大缓冲、候选历史缓存字符上限、最大输出长度和适用时的代码页；若另设候选条数限制，必须独立标明单位。保留游戏专用“延迟注入/等待目标模块就绪”，与文本刷新延迟分开；Mac按backend实际入口能力提供等待条件，不照搬Windows DLL名称或保证成功。全局默认与游戏覆盖分开；代码页对已指定UTF-16/UTF-32等流不产生误导。Windows额外Win32钩子单列为平台专用。
  - 验收：逐字输入能在刷新窗口形成整句；延迟接入只影响接入时机，等待超时/退出/取消能结束。调整缓冲不会永久等待；字符与条数限制不混用；超过输出上限有可查的过滤原因；配置编码与实际文本流声明分别显示，不适用代码页的流提示原因。

- **REQ-006 特殊码与JIT及直接读取** — P1；文档已有，平台语义适配；SRC-14；SCR-03、05、13。保存、解析、校验并管理H/B字符或字符串码、JIT方法/客体地址码、E内嵌标记和R直接读取码。保留旧Windows格式的兼容路径；Mac将逻辑选择器与架构专用地址/寄存器参数分开，不能把旧数值直接解释为Mac参数。
  - 验收：格式错误在安装前定位到字段；已插入并选择的规则可恢复；不支持的backend能力在安装前返回清晰状态；直接读取与执行点拦截有不同类型和诊断。

- **REQ-007 Mac bridge与执行环境能力状态** — P0；规划新增；SRC-C04至SRC-C08；SCR-04、21、22。支持native游戏的脚本/插件入口与可用外部attach，两条路径分开描述；增加compat_windows的Mac宿主＋同bottle Windows helper候选，Windows目标仍通过相应Windows提取器，不伪装成原生Mac注入。接入能力包含进程进入、模块符号发现、CPU/ABI取参、拦截和IPC，不缩成“载入dylib或启动helper就完成”。原生RenPy/NW.js优先验证语义脚本，Unity Mono/IL2CPP逐runtime验证，传统指令签名逐版本重定位；兼容路径按产品/Wine版本、bottle配置、PE目标与helper架构重验。
  - 验收：fixture验证只显示fixture状态；真实游戏按execution_environment、entry和lane分别证明启动、连接、取文、显示及回写，取文不能推导内嵌。CrossOver/Wine目标纳入独立compat_windows记录，未验证为规划中/实验性或未验证状态；拒绝/受限状态不会自动改签名、关闭系统保护或替换目标runtime来制造原包支持。

- **REQ-008 内嵌开关与流能力** — P1；文档已有；SRC-05、SRC-06；SCR-03、05、13、22。浮窗显示和游戏内回写是两个独立开关。只有提取器声明且目标验证具备回写能力的流才启用内嵌；仅内嵌时不强制显示浮窗，取文可用不能推导回写可用。
  - 验收：显示、内嵌两开关的四种组合行为明确；无回写能力时按钮禁用并说明；关闭内嵌后原文恢复，不继续发送过期回写。

- **REQ-009 内嵌等待与文本及字体** — P1；文档已有，新增失败语义；SRC-06、SRC-23；SCR-03、13、16。配置译文/原文组合、等待时限、每行字符上限、繁体/日式汉字转换、字体/相对大小、清空游戏文字。字体修改按引擎能力提供；内嵌处理走单独白名单，默认不套用全部去重与破坏性过滤。回写失败或超时保留原文继续游戏。
  - 验收：超时不无限冻结游戏；返回晚于时限的结果不能写到下一句；字体与编码问题分别诊断；同一输入在浮窗与内嵌可使用不同处理配置，清空文字是明确选择。

- **REQ-010 模拟器游戏** — P2；文档已有，Mac未验证；SRC-07与引入清单；SCR-03、04、05、13、22。规划NS/PSP/PSV/PS2/PS3接入，记录原生模拟器名称/版本/宿主架构、客体游戏ID/版本和JIT策略。保留按游戏规则的语义与字符处理，backend承担客体地址与宿主JIT映射；支持表可以搜索和报告问题。
  - 验收：不把模拟器支持等同全部游戏；更换模拟器版本后提示重新验证；客体游戏切换不会沿用上个游戏的文本流和词典；未支持时可继续使用OCR。

## OCR与其他输入需求

OCR既是US-10无需游戏的独立持续输入源，也给US-01与US-03提供补充能力。主流程从其他应用的全局快捷键/菜单直接进入屏幕选区层，拖框松手即开始；工作页用于任务查看、配置和恢复，绑定目标窗口为次级捕获模式。区域、OCR引擎与翻译服务均就绪后才执行持续识别，不以游戏连接为前提。原生捕获权限、遮挡、最小化、缩放和多显示器行为各自定义状态，不能照抄Windows截图实现的成功条件。

- **REQ-011 OCR范围** — P0；文档已有，独立实时流程补全；SRC-02、SRC-05、SRC-09、SRC-18；SCR-06、14。创建、移动、调整、显示/隐藏、清除和恢复上次范围；支持多区域独立状态、聚焦前后区域/鼠标附近区域/取消聚焦。主要入口是全局“框选实时OCR区域…”快捷键或菜单，直接在原前台应用所在目标屏幕唤起临时覆盖层；冻结待选择画面供定位，区域外暗化、内保留原画，显示十字准星与尺寸。拖出有效矩形松手即提交范围并开始持续OCR，无需额外确认或回主窗口点击开始；Esc在提交前取消。冻结画面只供定位，持续任务读取当前实时画面。屏幕模式保存显示器身份、屏幕坐标与缩放，不跟随应用；“绑定应用窗口…”是次级入口，先选目标再保存窗口内相对区域与缩放，按REQ-013跟随。主窗口工作页用于任务查看/配置/恢复。边框可调以覆盖完整文字并留识别内边距，示例的98%宽度不是固定选框算法。提供“暂停”“继续”“停止”“调整范围”和恢复已保存任务；停止保留范围配置，再次开始需检查捕获目标与权限。持续自动区域与临时一次区域分开保存和显示。
  - 验收：无游戏记录/HOOK时，两种模式均可完成框选→持续识别→SCR-01原文与实时译文；屏幕模式在普通应用前台直接进入覆盖层，拖框松手即开始而不打开主窗口；多区域独立识别和停止，隐藏框或HUD不删区、不停OCR。调整已有范围时暂挂受影响区域，Return应用新范围且隔离旧revision迟到结果，Esc保留旧范围/source并恢复先前运行/暂停状态；新建选择取消不创建/开始新OCR源。退出覆盖层恢复原前台焦点，选区层和HUD不进入捕获输入。显示器断开暂停相关区域并提示重选，不能识别错误屏幕区域。

- **REQ-012 OCR自动触发** — P1；文档已有且按源码核对为三种；SRC-18、SRC-C03；SCR-06、14。提供周期执行、分析图像更新、鼠标键盘触发后等待稳定。周期/图像分析用文本相似度抑制重复；事件触发稳定后默认强制输出，不受该阈值阻止。分别配置执行周期、图像稳定性、与上次OCR图像的一致性、文本编辑距离阈值、触发事件及等待延迟；绑定窗口时事件触发限目标应用前台，周期/图像模式按捕获能力可后台运行。图像变化和OCR文本变化是两层判断：动态背景不应让同一文字不断重译，逐字文字应在可读的稳定时机提交。快速画面保留最新待处理帧并限制积压；持续不稳定时提示调整稳定等待或改用周期模式，不无限显示“翻译中”，不承诺捕获短于采样间隔的每一帧。原文“四种”不是第四种待实现模式。
  - 验收：静态文字和仅背景动画不会无止境重译；逐字显示稳定后识别；快速连续变化时不排队展示早已过时的文本/译文，停止后迟到结果不刷新浮窗。参数切换即时可观察；事件模式与周期模式分别显示触发原因，强制触发绕过文本相似度的语义在UI中明确；记录捕获、识别、原文显示及译文显示时间，区分OCR与翻译服务延迟。

- **REQ-013 OCR窗口绑定** — P1；文档已有，Mac需原生适配；SRC-10；SCR-06、14。可绑定游戏、视频播放器、浏览器或其他应用窗口，无游戏上下文时使用全局语言、处理与翻译配置，不制造游戏时长记录。绑定后仅捕获选定窗口及其区域，区域随窗口移动；缩放或resize后校正边界，无法确定时暂停并请用户调整。窗口被遮挡/最小化时按backend能力继续、暂停或提示不可捕获，切前台应用不隐式更换目标。可选择关联已有游戏词典、语言与时长，但不是OCR启动条件。捕获失效、无可用图像/黑屏与正常“未识别到文字”分别反馈；不能自动降级为整屏捕获。
  - 验收：浮窗位于OCR区域之上时不产生自反馈；移动目标窗口区域同步；目标关闭、窗口身份失配或无可用图像后暂停相关捕获并保留配置/上次可读结果，重新选择或恢复需匹配目标身份。不支持遮挡捕获的backend明确提示；授权成功或窗口仍存在不能冒充取得可识别图像。

- **REQ-014 OCR原地翻译** — P1；文档已有；SRC-18；SCR-06、14、18。按识别文本框的位置、角度、大小显示译文，仅覆盖文字区域；背景、颜色、对齐样式在区域菜单与设置同步。多区域分别显示，覆盖层鼠标穿透，捕获排除自身译文。
  - 验收：横向和倾斜fixture位置正确；改变样式两处同步；重识别不会把自身译文作为原文；禁用后覆盖层消失且游戏点击正常。

## 完整用户流程

### 初次启动与配置

首次启动建立默认配置并提供可见的SCR-01常驻浮窗；没有输入时显示等待输入，用户可以立即从更多菜单pin置顶、设置显隐快捷键，或执行“框选实时OCR区域…”进入屏幕选区层，无需先打开主窗口或添加游戏。用户在SCR-12“通用”选择界面与源/目标语言，再在SCR-15配置至少一个翻译器。需要指定不同配置目录时使用SCR-20或`--userconfig`等价入口，不把高级配置管理作为首次翻译的前置。连接测试先报告网络/凭据/模型状态，样例译文可在无游戏时预览。需要本机OCR或分词时，SCR-14/SCR-09分别安装相应资源；用户不使用的输入源不要求一次申请全部权限。SCR-21显示当前版本与未完成资源，SCR-22在用户检查游戏接入时按native/compat_windows解释目标能力。完成后可用SCR-07手动句子验证普通翻译管线，或直接进入以下实时OCR流程；App启动不自动扫描并注入游戏。

验收关联：REQ-016、018、020、021、029、041、042、046、049、052、054。无游戏、无HOOK和无OCR权限时，浮窗与手动翻译仍能工作；资源安装失败不会阻止用户保存配置。

### 游戏的HOOK会话

用户从SCR-02选择游戏启动，或在SCR-04选已运行进程。产品先显示目标身份、架构、runtime和接入能力。可用脚本/插件入口与外部attach按目标条件选择；进入游戏后的bridge协商取文/回写能力，接入日志可在SCR-22检查。SCR-05开始显示候选流，用户让游戏输出一段文本，选择正文与必要的人名流，SCR-01展示合并原文与翻译。选择保存到SCR-03，下次仅恢复身份能匹配的流。连接失败不会取消游戏库记录，用户可转绑定窗口并用OCR。

compat_windows主路径：用户选择已有游戏/bottle并点击连接，Mac客户端检查兼容环境与实际目标身份/PE架构→核对同源资源并自动选择helper64/Host64接收端及目标匹配的injector32/64和Hook32/64→启动同bottle接收组件并完成版本/身份握手→连接Windows目标→等待实际文本→进入SCR-05选流。若首次不能可靠关联bottle，SCR-04先呈现可取消的选择确认，不猜测另一个bottle；确认后按同一流程继续。SCR-03保存环境、bottle引用、Windows目标和专用配置，下次“运行并连接”自动完成启动/接入；helper只作为客户端管理组件，不要求额外Windows客户端、位数手选或手工复制DLL。缺32资源或组合不符时先修复组件包再重新检查；修复不自动等于连接或取文成功。helper失败先提供重试、修正bottle、诊断和OCR，备用手动启动仅为故障兜底。取消接入不杀游戏，断开仅清理本次自有helper/agent，不关闭整个bottle；注入后清理无回执时保留未知状态。x86扩展已有同源双目标工程实现及受控局部观察，自动化产品接入和原版游戏仍待验收；任何局部观察不扩展到任意CrossOver/Wine版本的完整兼容性。

验收关联：REQ-002至007、037、043、052、055。启动游戏、helper/bridge就绪、连接目标、收到文本和译文出现为独立状态；任一失败有单独恢复动作，native与compat_windows分别留证。

### 内嵌翻译

用户在SCR-05或SCR-03选具备回写能力的流，并独立启用显示/内嵌。SCR-13设置等待时限、排版与字体能力，SCR-16确认内嵌处理白名单。输入事件带句子身份进入翻译；在等待窗口内得到有效结果才回写。超时、断连或身份失配都保留原文，让游戏继续；晚结果可进入历史或浮窗，不能写到下一段游戏文本。

验收关联：REQ-008、009、022、027、055。测试分别证明取文、回写、超时回退和退出恢复；只能取文的提取器不能启用此流程。

### 无游戏实时OCR翻译

这是US-10的完整独立工作流，可用于课程视频、会议字幕、浏览器或其他应用的画面文字。用户不需要建立游戏记录、连接进程、安装游戏helper或等待HOOK成功。这里的“框选”指用户划定屏幕/窗口中的识别矩形，常驻翻译浮窗是另一个用于阅读原文和译文的窗口。

| 步骤 | 用户操作与产品结果 | 页面归属 |
| --- | --- | --- |
| 进入 | 在课程视频、会议或浏览器等原前台应用中，用全局“框选实时OCR区域…”快捷键（设计建议⌥⌘O，可改）或输入/菜单栏/浮窗更多菜单同名命令，直接进入目标屏幕临时覆盖层，不先打开主窗口。工作页负责任务查看、配置、恢复；“绑定应用窗口…”为次级入口。 | SCR-06、18、01 |
| 拖框与开始 | 冻结待选择画面供定位，十字准星随指针反馈，矩形外暗化、内保留原画并显示尺寸。拖出有效矩形松手即提交新范围并将默认持续source设为OCR，关闭覆盖层、恢复原前台焦点，从当前实时画面识别；不增加常规确认按钮。Esc在提交前取消，保留旧区域/source与原运行/暂停状态，不创建新任务。屏幕固定区域记录显示器/坐标/缩放；可选窗口绑定记录identity/相对范围，不能失败便改抓整屏。 | SCR-06、01 |
| 识别与翻译配置 | 复用当前OCR引擎、识别语言、触发模式、翻译服务与目标语言；需要更改时到SCR-14/15，但日常框选不要求先经过设置页。首次需要捕获时请求屏幕权限，并说明在线OCR是否发送选区图像；缺权限/资源/服务给具体修复入口，不额外增加自定义确认步骤。 | SCR-06、14、15 |

| 调整与后台运行 | “调整范围…”再次唤起屏幕选区层，暂挂受影响区域；Return应用新范围并以新revision恢复先前运行/暂停状态，Esc取消保留旧范围/source及原状态，结束恢复原前台焦点。其他区域不因调区被停掉。周期/图像更新模式在客户端失焦或主窗口关闭后按捕获能力持续工作；输入事件模式只观察指定目标前台事件。跨显示器/DPI变化和断开时校正或暂停提示，不把旧坐标用于另一屏。 | SCR-06、14、01 |
| 故障恢复 | 权限拒绝/撤销、窗口关闭/身份变化、最小化或遮挡不支持、黑屏/无可用图像、OCR失败与翻译失败分别反馈。捕获不可用暂停相关范围，提供重新检查、重选窗口/范围入口；翻译服务失败时原文仍可读/复制并可重试，旧句译文标明归属。恢复需重验目标与权限，不自动扩大捕获范围。 | SCR-06、14、01、21 |

默认读取当前最新画面，稳定等待与文本去重共同避免逐字重复和背景动画反复请求；快速变化不会积压过时帧并逐一覆盖浮窗。OCR、文本处理、翻译调度与浮窗共用普通输入管线，但不经过游戏attach/HOOK链路；可选原地翻译是REQ-014的另一显示方式，不替代这里的常驻浮窗交付。

验收关联：REQ-001、011至016、020、021、024、041至043、046、054；SCR-01、06、14为核心路径，SCR-15、18承载服务/快捷键配置。对应TC-017、018、019、020、032、040、041、043、046；必须在无游戏/HOOK的实际应用画面中证明“持续变化→原文→实时译文”，单张测试图或引擎安装成功不能替代。

### 一次OCR与HOOK补充

当HOOK遗漏选项时，用户从浮窗更多菜单或快捷键执行“一次OCR…”，框选临时区域并只识别一次，结果可在浮窗或原地显示，原HOOK采集保持运行。复用上次一次区域无需重新框选；这条临时输入不等于“开始实时翻译”，两条命令分开命名。

验收关联：REQ-001、015、043；TC-017、043。持续OCR和一次OCR使用不同运行范围，一次操作结束不会停止或替换原默认持续源。

### 翻译质量调整

用户从当前句打开SCR-16，查看原始输入、逐处理器结果和最终送入翻译的文本；启用或调整去重/替换并实时预览。专有名词在对应阶段加入全局或游戏词典，SCR-03确认继承规则。SCR-15复制LLM接口配置来比较prompt或模型，必要时重置上下文。重译会标记使用的新配置版本，SCR-08保存不同版本结果与人工修正。

验收关联：REQ-021至028、045。参数和规则调试不会把游戏输入事件本身改写，也不会导致缓存中旧结果冒充新配置输出。

### 文件翻译任务

用户在SCR-07添加受支持文件，检查结构、编码和待译片段，选择引擎及SRT双语方式。开始后展示文件级与片段级进度，可取消、暂停或恢复；失败项单独重试。最终结果先验证格式，另存到用户选择的位置；原文件不被覆盖。任务使用独立上下文范围，不能污染当前游戏LLM对话。

验收关联：REQ-019、022、024、045、050。输出文件既有译文也保留原结构；中止后不生成无标识的不完整“完成文件”。

### 学习与制卡

用户在SCR-01或SCR-08阅读原文与注音，悬停或选词打开SCR-09。辞书按来源逐个返回，原型查询和词面均可查看。选择制卡后SCR-10带入可用释义、句子、译文、读音、音频或截图；用户补足缺失字段，选择牌组与模板并预览，然后发送AnkiConnect。Anki同步是后续外部服务流程，SCR-10提供配置与连接帮助，不与制卡成功混为一体。

验收关联：REQ-029至034、043、045。查词、制卡、媒体上传与外部同步各有状态；超时重试不会重复生成同一笔记。

### 游戏管理与日常恢复

用户在SCR-03调整启动与专用设置，compat_windows同时核对bottle引用及Windows目标；预览元数据候选，选封面、角色词条和标签。运行会话绑定时记录时长；结束、暂停、休眠或崩溃按计时策略封闭区间。SCR-11保存游戏或全局备忘，SCR-08保存翻译记录。再次运行并连接恢复游戏配置和浮窗位置，失效路径、bottle、流或backend给出修复入口，不因恢复设置就自动注入其他目标。

验收关联：REQ-028、037至045、052。游戏身份不依赖临时PID；崩溃恢复不会制造数小时无界计时，也不会丢已提交记录。

### 网络服务与配置迁移

用户在SCR-19启用本机服务，查看端口、可用API与连接终端；局域网访问需要选择范围和认证。外部文本输入与浏览器工具任务走统一管线，网络客户端不会获得游戏进程控制。迁移时用户在SCR-20选择源目录和范围，先看预检/冲突/平台差异，备份后提交；更新在SCR-21检查版本配套和迁移备份，失败可恢复。

验收关联：REQ-047至055。远程访问关闭后外部客户端断开；导出/迁移默认脱敏；更新失败不会留下宿主与bridge不兼容的活动组合。

## 输入与配置及数据规则

1. **不可变原文**：采集文本、处理结果、服务请求文本、译文与回写文本分开保存；不会为方便显示而永久覆盖原始来源。
2. **身份和次序**：事件包含会话、游戏、输入源、文本流和句子标识；多流按选择顺序合并，同一流保持次序。目标身份包含execution_environment；compat_windows还绑定bottle、Windows target及helper/bridge实例，与Mac host窗口身份分开。新会话或bottle重建后，旧异步结果不得更新新会话显示或回写。
3. **配置生效范围**：全局配置、独立用户配置目录、游戏覆盖和临时会话值可区分；跟随默认、合并词典和完全替换分别有明确定义。首次从跟随切到自定义且无专用备份时复制当前有效值；已有自定义备份时恢复备份。返回跟随保留备份，全局更新不覆盖它；保存后的有效值能追溯来源。
4. **暂停语义**：自动采集暂停不等于断开、不等于关闭翻译；手动输入仍可执行。关闭翻译总开关取消未开始请求，已在途结果按当前显示和记录策略处理，不回写已关闭的内嵌流。
5. **持久数据**：游戏库、规则、词典、备忘、人工译文与游玩记录属于用户数据；候选流缓存、下载缓存和模型资源有不同清理入口。清缓存不能删人工修正。
6. **资源与执行**：模型/词典/插件有版本、来源和运行条件；导入数据只解析，不自动运行其中脚本。用户启用的Python/JS/C#插件不因宿主改为Rust而丢失配置来源。

## 路线与交付门槛

优先级不代表功能价值高低。P0建设可靠的输入、核心与维护边界；P1承接完整日常工作流；P2补足深度生态和平台专用能力。每一阶段保留后续功能的页面归属、配置schema与能力状态，避免后续重做信息架构。

| 路线 | 需求集合 | 交付门槛 |
| --- | --- | --- |
| P0 核心与可检查接入 | REQ-001、002、003、004、005、007、011、015、016、017、018、020、021、025、027、037、041、043、052、054、055、056 | 手动/剪贴板/OCR与至少一个合法可用的HOOK目标在测试范围内完成输入到显示；Rust核心、配置与游戏身份可复现；Macbridge分别为native与compat_windows提供fixture/真实目标证据，兼容环境自动helper流程可取消并隔离bottle；未覆盖项目保持未验证，无凭据泄漏和无限游戏等待 |
| P1 日常完整工作流 | REQ-006、008、009、012、013、014、019、022、023、024、026、028、029、030、032、034、038、039、040、042、045、046、048、049、050、051、053 | 内嵌限已验证提取器；文件结构、学习制卡、多服务、规则继承、浮窗与快捷键、数据迁移更新按各验收通过；Mac不支持的系统实现有真实状态与替代入口 |

交付范围由发布清单列出具体平台、execution_environment、backend、插件版本和目标游戏，不以P0/P1名称替代覆盖清单；compat_windows还固定兼容产品/Wine版本及bottle条件。Windows的已有库或规则仍需在新Rust宿主中回归；Mac未完成项不得通过照抄Windows支持表获得“已验证”状态。

P0/P1表示完整需求的优先级，不等于开发分期。第一期D1必须交付最小可运行应用：可见常驻浮窗、更多菜单pin置顶、游戏或其他应用前台时全局快捷键显隐，并在CrossOver/Wine与Mac原生真实游戏分别取得持续实时文本、送达浮窗。D1基础HUD实际验收、GC兼容接入与GN原生接入全部通过，才形成GE的GO决策；fixture、启动/连接成功或OCR不得代替直接游戏文本。基础HUD与接入探索并行，不等到GE后补做；GE后再补齐GU完整四页SCR-01/04/08/15的其余选型验证并完成D1退出交付。未满足D1退出门槛时只继续最小支撑、实验与技术改线，不开放D2–D6生产开发。D2明确交付US-10“无游戏实时OCR翻译”的完整端到端流程；产品运行时该流程独立于游戏/HOOK，不以游戏连接成功为条件。具体范围、依赖与证据在[独立开发分期表](05-development-plan.md)、[架构](03-client-architecture.md)和[测试计划](04-test-plan.md)追溯。当前应用交付与PoC均未执行，正式游戏支持及内嵌继续按runtime/lane分别验收。
